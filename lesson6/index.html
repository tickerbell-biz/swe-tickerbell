Lesson 6

From static website to secure, scalable web application

A practical architecture lesson based on a real product decision: preserve what works, then add identity, authorization, data, and deployment automation one layer at a time.

The decision

The existing GitHub Pages site is successful as a public journal. We are adopting a new architecture because the learning goal has advanced and the product now needs authenticated learners, team content management, admin analytics, protected documents, and stored progress.

Engineering lesson: architecture should change because requirements changed—not because a larger stack looks more impressive.

Static website versus web application

Static websiteWeb application
Publishes the same files to every visitorReturns data based on identity and permissions
No server-side business logicAPI validates actions and applies rules
Public downloadsPrivate files delivered through controlled access
Good for public contentRequired for progress, CMS, analytics, and accounts

Architecture

Firebase Hosting serves the public interface. Auth0 signs users in. The browser sends an access token to the FastAPI service on Cloud Run. The API verifies the token and role before reading Firestore or creating controlled access to a private Cloud Storage object.

What makes it secure

  • Universal Login handles passwords outside our frontend.
  • The API checks authentication and authorization on every protected request.
  • The backend uses a limited Google service account.
  • Secrets remain in Secret Manager.
  • Private files remain outside public repositories.
  • Audit records explain important administrative actions.

Build order

  1. Review these static page prototypes locally.
  2. Configure Auth0 and prove login/logout.
  3. Connect Firebase Hosting to GitHub Actions in a separate implementation step.
  4. Create a private backend repository and FastAPI health endpoint.
  5. Protect one profile endpoint with an Auth0 access token.
  6. Store one learner profile in Firestore.
  7. Expand role checks and add private file delivery.

Practical exercise

Open each demonstration page and write down what data it would need. Mark every item as public, personal, team-only, or admin-only. Then identify which API endpoint must authorize access. This converts page design into a security model before coding begins.

Completion criteria

  • You can explain authentication versus authorization.
  • You can name the responsibility of every selected service.
  • You understand why protected data cannot live in the public frontend repository.
  • You can describe the request path from login to Firestore.
